Part AThe project

Who the client is, what is wrong with what they have, what we are building instead, and the business words you will hear every day.

A1. The client and the problem

The client is a DMC (Destination Management Company) based in Morocco, with branches in Agadir and Marrakech. A DMC runs the "ground" part of a trip. It buys hotel nights, transfers, excursions, guides and vehicles from local suppliers, packages them (for example as circuits), and sells them to foreign tour operators, travel agencies, online travel agencies (OTAs such as Expedia) and directly to travellers. It earns the margin between what it buys at (the cost) and what it sells at (the sale price).

Today the agency runs "Agence 2024", a Windows desktop application.

Old systemWhat it means for us
VB.NET WinForms, .NET Framework 4.8, ~140 formsBusiness logic sits in click handlers and is copied between forms. Nothing can be reused.
SQL Server 2017: 127 tables, 780 stored proceduresThe rules live in procedures. About 40 procedures that the code calls do not exist.
112 of 127 tables have no primary key, and there are no foreign keysDuplicates and orphan rows are possible. This is why the new system starts empty (ADR 0005).
One database per season (agence_sti_2026)Reports across years and contracts that cross November need workarounds.
Crystal Reports, 93 .rpt filesReplaced by a PDF library in the new system.

The five problems that drive the whole project

  1. Contracts are not a price source. Several versions of the same contract circulate, so prices are typed and checked by hand. The client wants prices calculated automatically, and that only works if exactly one version is valid on any date.
  2. Invoicing is unsafe. Issued invoices get overwritten, cancelled numbers get reused, and two operators can receive the same number because the code reads the counter and then increments it in two separate steps.
  3. Money is stored as float, which causes rounding errors on totals. There is no real VAT. Closed months can be reopened by anyone.
  4. No itinerary. A booking file is a list of sales lines, so vouchers, transfers and lists are retyped by hand.
  5. Cash is unsafe. Some procedures corrupt data (an UPDATE without a WHERE recalculates every cash voucher). There is no bank reconciliation and no closing. Passwords sit in plain text in app.config.

Each problem becomes a rule in CLAUDE.md. Point 1 becomes "one active contract version per date". Point 2 becomes "invoice numbers change only inside a transaction with a row lock". Point 3 becomes "money is decimal / numeric(18,2)". Knowing the reason behind each rule lets you defend it when a shortcut looks tempting.

What we build instead

We build three front ends on one backend. All of them get prices, availability and bookings from the same rules and the same database.

A3. Your two roles: delivering for a client, and learning

This project has two goals that sometimes pull against each other. The client pays for working software. You also want to come out of it as a much stronger engineer. The plan in docs/development-strategy.md builds learning into delivery ("learn just in time"). These habits keep the two goals aligned:

  1. Estimate with learning included. The first slices will be slow because every concept is new. Later slices reuse the same path and go faster. Tell the client this up front, then show it with the bi-weekly demos.
  2. Demo every two weeks on the test environment, using their real contracts and circuits as examples (not as data in the code). A demo catches wrong assumptions while they are cheap to fix. Forward Deployed Engineers live by this habit.
  3. Write decisions down (ADRs). When the client asks "why did you do it this way?" six months from now, the ADR answers, and it protects you too.
  4. Keep the client's assets in the client's name. The cloud subscription, domain names, AI provider account, WhatsApp business account and, ideally, the GitHub organisation should belong to the client, with access granted to you. Agree in writing who owns the code. (This is good practice, not legal advice. Check your contract.)
  5. Never put real data in code, tests or prompts. Use invented hotels and guests. Guest data falls under Moroccan Law 09-08 (CNDP).
  6. Use Claude Code as a tutor, not a replacement. Ask it to explain a concept with an example from this code before it writes the code. Write or review the domain test yourself. Read every diff and ask "why this way?". Let it do the repetitive work (mappings, Helm boilerplate, form plumbing) and spend your own attention on pricing, versions, billing and security.
  7. Explain to learn. After applying a concept, write 5–10 lines in docs/learning/<concept>.md in your own words, with a link to the code. Reread it a month later.

The rules card (from CLAUDE.md)

Architecture
  • Layers: Domain → Application → Infrastructure → hosts. Dependencies point inward.
  • Domain uses no framework (no EF Core, no ASP.NET). Application never references Infrastructure.
  • Modules are folders in each layer. They talk through application interfaces or domain events only.
  • Rules live in entities and value objects.
  • One repository per aggregate. No generic repository, no MediatR or AutoMapper.
  • Expected failures return a Result. Exceptions are for bugs and infrastructure.
  • Architecture tests enforce all of this.
Data
  • Money: decimal / numeric(18,2). Rates: numeric(18,6). Never float.
  • Stay dates: DateOnly / date. Moments: DateTimeOffset / timestamptz in UTC. Use TimeProvider, never DateTime.Now.
  • Primary keys, foreign keys, and check, unique and exclusion constraints everywhere.
  • snake_case names.
  • Invoice numbers, allotment and payments change only in transactions with row locks, never from cache.
  • Contracts, circuit templates and vouchers are versioned.
AI
  • AI creates drafts only. A logged-in human approves, and the API enforces it.
  • The guest assistant sees published, public data only.
  • MCP tools are read-only. No free-form SQL.
  • Every AI feature has an eval set in tests/evals/.
Working
  • Thin vertical slices: domain test first.
  • One change = one pull request.
  • Run dotnet test and front-end tests before calling a task done.
  • Ask before adding a dependency or project, or changing an ADR.
  • No real data or secrets anywhere.

Part BThe process

How the work is ordered (phases and gates), how one slice is built, what a working day looks like, and when a task counts as done.

B1. The roadmap: seven phases, each with a gate

The phases follow the dependencies between modules. You cannot price without contracts, book without prices, or invoice without bookings. A phase ends only when its gate can be shown to the client on the test environment. "Code complete" does not count.

Inside phase 1 the first slice is the walking skeleton: "create a city and list cities". The business logic is trivial, but the slice crosses every layer and is deployed to Kubernetes. Infrastructure problems (sign-in, migrations, containers, networking) then show up in week one rather than at go-live. Part D plans this slice in detail. The second slice, the first real one, is a hotel contract with one season and one rate, and the pricing engine returning a price for a stay.

B2. How one vertical slice is built

A vertical slice is one feature built through every layer, from database to screen to deployment, before the next feature starts. The alternative, "horizontal" layering (all tables first, then all services, then all screens), delays the first working feature by months and hides integration problems until the end.

Inside each slice the order is fixed:

#StepWhat you produceWhy in this order
1Domain testA failing unit test that states the business rule ("a city name cannot be empty")Forces you to decide the rule before writing code. Runs in milliseconds.
2Domain codeEntity / value object that makes the test passThe rule lives in one place, with no framework.
3ApplicationUse case (command or query) + interfaces it needs, tested with fakesOrchestration without a database.
4InfrastructureEF Core mapping, migration, repository; integration test against real PostgreSQLProves constraints and mapping.
5APIEndpoints, permissions, OpenAPI, logsThin: it only translates HTTP to use cases.
6React screenPage using the generated API clientThe user can see it.
7Helm valuesConfig / secrets / routes the feature needsIt runs on the test cluster.

B3. Your daily loop

  1. Pick one small task from the current slice, half a day to two days of work.
  2. Create a branch from an up-to-date default branch.
  3. Explain first. If the task introduces a new concept, read its card in Part E and ask Claude Code to explain it with this code.
  4. Write the domain test (or review the one Claude proposes), then the code.
  5. Run all tests locally, then commit with a message that says why.
  6. Push and open a pull request. CI runs build, unit, integration and architecture tests.
  7. Review your own diff against the definition of done (B4), then merge.
  8. CD deploys to the test environment once it exists (end of slice 1). Check the feature there.

git add -p                                    # stage hunk by hunk: you read every change

gh pr merge --squash --delete-branch          # one clean commit on master
Size of a pull request

Aim for something you can review in 15 minutes: usually under ~400 changed lines, excluding generated files (migrations, API client). If a PR grows past that, split it. Example: "domain + tests" in one PR, "EF mapping + migration" in the next.

B4. Definition of done

A task is done only when every box is ticked. Each item says how to check it.

  • Tests pass: dotnet test backend/Agency.slnx and pnpm -C frontend -r test are green locally and in CI, including architecture tests.
  • No warnings: the build treats warnings as errors (TreatWarningsAsErrors in Directory.Build.props), so a warning fails the build. Same for the TypeScript type check and lint.
  • OpenAPI updated: new or changed endpoints appear in the OpenAPI document with request/response types and error codes, and the generated front-end client is regenerated.
  • Permissions checked: every endpoint has an authorization requirement. An integration test shows that an anonymous call gets 401 and a user without the role gets 403.
  • Meaningful logs: important actions log one structured line with IDs (no personal data, no secrets).
  • Works on the test cluster: after deployment, you have clicked through it there.
  • ADR if a decision was made, and analysis-and-design.md updated if the design changed.

B5. Writing an ADR

An Architecture Decision Record is a short file that records one important decision: what was decided, why, and what was rejected. It is cheap to write and saves hours of "why is it like this?" later. Write one whenever you choose between real alternatives that would be costly to change: a library, a pattern, a hosting choice, a security approach. Do not write one for code style.

docs/adr/0007-guid-v7-primary-keys.md

# ADR 0007: GUID v7 primary keys

Status: Accepted · Date: 2026-10-20

## Decision
Entities use Guid v7 identifiers generated in the application (Guid.CreateVersion7()),
stored as PostgreSQL uuid.

## Why
The ID exists before saving (useful for events and links); IDs cannot be guessed or counted
by partners; v7 is time-ordered, so inserts stay index-friendly unlike random v4.

## Rejected alternatives
bigint identity columns (exposes counts, needs a DB round trip for the ID); Guid v4 (random index order).

To change a decision, add a new ADR with Status: Accepted · Supersedes 0007 and set the old one to Superseded by 00xx. Never edit history.

// src/Agency.Domain/Catalogue/City.cs — the entity guards its own rules
public sealed class City
{
    public const int NameMaxLength = 100;
    public Guid Id { get; private set; }
    public string Name { get; private set; } = null!;

    private City() { }                                  // for EF Core materialisation

    public static Result<City> Create(string? name)
    {
        var trimmed = name?.Trim() ?? "";
        if (trimmed.Length == 0)            return CityErrors.NameRequired;
        if (trimmed.Length > NameMaxLength) return CityErrors.NameTooLong;
        return new City { Id = Guid.CreateVersion7(), Name = trimmed };
    }
}

public static class CityErrors
{
    public static readonly Error NameRequired = new("city.name_required", "City name is required.");
    public static readonly Error NameTooLong  = new("city.name_too_long", "City name is at most 100 characters.");
    public static readonly Error NameTaken    = new("city.name_taken", "A city with this name already exists.");
}
Why is "unique" not checked here?

An entity sees only itself. It cannot know which other cities exist. Uniqueness is a rule across many rows, so it is enforced in two places. The use case checks first, to give a friendly error. The database unique index guarantees it even when two requests arrive at the same moment (task 5). This "check plus constraint" pattern comes back for contract versions and invoice numbers.

// src/Agency.Application/Catalogue/CreateCity.cs — a plain handler class, no MediatR
public sealed record CreateCityCommand(string Name);

public sealed class CreateCityHandler(ICityRepository cities, ILogger<CreateCityHandler> logger)
{
    public async Task<Result<Guid>> HandleAsync(CreateCityCommand command, CancellationToken ct)
    {
        var created = City.Create(command.Name);
        if (created.IsFailure) return created.Error;

        if (await cities.NameExistsAsync(created.Value.Name, ct))
            return CityErrors.NameTaken;

        cities.Add(created.Value);
        var saved = await cities.SaveChangesAsync(ct);
        if (saved.IsFailure) return saved.Error;

        logger.LogInformation("City {CityId} created", created.Value.Id);
        return created.Value.Id;
    }
}

E1. Architecture and ways of working

Vertical slice and walking skeleton Whole project

Build one feature through every layer before starting the next. The very first slice is deliberately trivial but deployed for real.

Why we need it hereA single developer can easily spend months on "the database" or "the framework" with nothing to show. Slices produce something the client can see every two weeks. The walking skeleton (a term from Alistair Cockburn) is a minimal end-to-end path that "walks": a city typed in a browser on the cluster reaches the database. Every later slice reuses that path and only adds business logic.
In this projectSlice 1 = cities. Slice 2 = one hotel contract with one season and one rate, priced for a stay. Each slice follows B2's order: domain test → domain → application → infrastructure → API → screen → Helm values.
Watch outDo not gold-plate the skeleton (no generic CRUD framework "to save time later"). Do not skip deployment "until later": finding deployment problems early is the whole point.

Clean Architecture Deep diveTask 1

Organise code in layers where every dependency points inward, toward the business rules. Frameworks and databases are details on the outside.

Why we need it hereThe old system put rules in stored procedures and click handlers, so you could not test a price without a database and a form. We want pricing, contract versions and invoices as plain C# that runs in a millisecond-fast unit test. We also want to swap infrastructure (AI provider, storage, WhatsApp provider) without touching business code.
Figure E1 — Each ring may use only rings inside it. Arrows of "uses" always point inward.
How it works: the trick that makes it possibleThe Application layer needs to save a city, but it must not know about EF Core. So Application declares an interface (ICityRepository), and Infrastructure implements it. At start-up the host connects the two through dependency injection. The compile-time dependency points inward (Infrastructure → Application), even though at run time Application calls Infrastructure. This is the Dependency Inversion Principle, the "D" in SOLID.
In this projectProjects Agency.Domain → Agency.Application → Agency.Infrastructure → hosts. Project references make wrong dependencies impossible to compile in one direction, and architecture tests catch the rest (for example a using Microsoft.EntityFrameworkCore sneaking into Domain through a package).
Watch outThe common failure is over-layering: five classes and three mappings to list cities. analysis-and-design.md warns about this explicitly. Simple reads can be thin queries. Use the full ceremony where rules exist (pricing, billing).
ReadMicrosoft's "Common web application architectures" guide (Clean Architecture section). Robert C. Martin, Clean Architecture, chapters on the Dependency Rule.

Modular monolith Task 1

One deployable application and one database, divided inside into business modules with clear borders.

Why we need it hereADR 0001: one developer and tightly connected rules (a booking needs prices, an invoice needs bookings). Microservices would add network calls, distributed transactions and many deployments for no benefit. The borders still matter, though: without them you get the old system's "everything touches everything".
In this projectModules are folders in each layer: Agency.Domain/Catalogue/, Agency.Domain/Contracts/, and so on. A module never uses another module's internals. It calls that module's application interface, or reacts to a domain event. A good habit: give each module its own PostgreSQL schema (catalogue.cities), so ownership is visible in the database too.
Watch out"Modular monolith" is not the same as "several hosts". The six hosts (BackOffice, PartnerApi …) are different entry points into the same modules. Use internal for types that other modules must not use, and add architecture tests for module borders once there are two modules.

Entity, invariant, factory method Task 3

An entity has an identity that stays the same while its data changes. An invariant is a rule it must always satisfy. A factory method is the single door through which valid instances are created.

Why we need it hereCLAUDE.md forbids "anemic models" (classes with public setters and all rules in services). If anyone can write city.Name = "", the rule "name not empty" must be re-checked everywhere, and one place will forget. If the only ways to create or change a city check the rule, an invalid city cannot exist.

Result pattern vs exceptions Deep diveTask 3

Return expected failures as a value (Result) that the caller must look at. Keep exceptions for bugs and broken infrastructure.

Why we need it here"Name already taken", "contract overlaps", "credit limit exceeded" are normal business outcomes, not crashes. If they are exceptions, the method signature hides them, callers forget to catch them, and they cost a stack trace each time. A Result makes the failure part of the signature: Task<Result<Guid>> says "this can fail, deal with it".
How it worksA small type we write ourselves in the Domain (no package needed):
public sealed record Error(string Code, string Message);

public class Result
{
    protected Result(Error? error) => Error = error;
    public Error? Error { get; }
    public bool IsSuccess => Error is null;
    public bool IsFailure => !IsSuccess;
    public static Result Success() => new(null);
    public static implicit operator Result(Error error) => new(error);
}

public sealed class Result<T> : Result
{
    private readonly T? _value;
    private Result(T value) : base(null) => _value = value;
    private Result(Error error) : base(error) { }
    public T Value => IsSuccess ? _value! : throw new InvalidOperationException("No value on failure.");
    public static implicit operator Result<T>(T value) => new(value);
    public static implicit operator Result<T>(Error error) => new(error);
}

The implicit operators let you write return CityErrors.NameTaken; or return city;. At the API edge, one function maps error codes to HTTP: *.name_taken → 409 Conflict, validation codes → 400, *.not_found → 404.

Watch outDo not wrap infrastructure errors (database down, timeout) in Results. Those are exceptions, handled once by the global exception handler (→ 500). Reading .Value on a failure throws, because it is a bug. The error Code is a stable contract with the front end and partners: never rename one casually.

async/await and CancellationToken Deep diveTask 4

Non-blocking waiting for I/O (database, HTTP, AI). The thread is released while the database works, and resumes when the answer arrives.

How it worksA web server has a limited pool of threads. If each request blocks a thread while waiting 20 ms for PostgreSQL, the pool runs out under load. With await db.SaveChangesAsync(ct) the method returns a Task, and the thread goes back to the pool to serve other requests. When the database answers, the rest of the method continues (possibly on another thread). The compiler rewrites your method into a state machine to make this work.
CancellationTokenIf the user closes the browser tab, ASP.NET Core cancels HttpContext.RequestAborted. In minimal APIs, add a CancellationToken ct parameter and it is bound automatically. Pass it down to every async call (ToListAsync(ct)), so abandoned work stops instead of wasting the database's time. In slice 6 the same mechanism will stop an expensive AI call nobody is waiting for.
Rules"Async all the way": never call .Result or .Wait() on a task, because that risks deadlocks and thread starvation. Name async methods …Async. Return Task, not async void (except event handlers). Do not use Task.Run to "make things async" in web code.
ReadMicrosoft docs: "Asynchronous programming with async and await"; "Cancellation in managed threads".

EF Core: DbContext and change tracking Deep diveTask 5

An ORM (object-relational mapper) that maps C# classes to tables, translates LINQ to SQL, and tracks changes to loaded objects so that SaveChanges writes them.

How it worksAgencyDbContext has one DbSet<City> per aggregate root. When you load an entity, the context's change tracker keeps a snapshot. That makes the DbContext a natural unit of work: everything changed during one request is saved together or not at all.
In this projectThe mapping lives in IEntityTypeConfiguration<T> classes in Infrastructure (the Domain stays clean). The Npgsql provider talks to PostgreSQL. UseSnakeCaseNamingConvention() turns City.Name into column name. Queries that only read use AsNoTracking() (faster, no snapshot).
Watch out

  • Translating database errors: a unique violation arrives as DbUpdateException wrapping a PostgresException with SqlState == "23505". The repository catches exactly that and returns CityErrors.NameTaken. Everything else stays an exception.
  • Watch the SQL that LINQ generates. N+1 queries (one query per row in a loop) are the classic ORM performance bug.

Collations and case/accent-insensitive text Task 5

E4. Security

OAuth 2, OpenID Connect, JWT Deep diveTasks 7, 9

OAuth 2 lets an application get an access token to call an API. OpenID Connect (OIDC) adds sign-in on top, meaning who the user is. A JWT is the token format: signed JSON the API can verify by itself.

Why we need it hereStaff, partners (by API), the MCP client and later guests all need to prove who they are, and the API must decide what each may do. We do not want to store passwords or write login screens ourselves. A dedicated identity provider (Keycloak, Entra ID) does that, and our API only checks tokens.
The flow in slice 1: authorization code + PKCE
  1. The user opens the back office. The SPA sees no session and redirects the browser to Keycloak's login page, with a random code verifier hashed into a code challenge (that is PKCE).
  2. The user signs in on Keycloak. Our app never sees the password.
  3. Keycloak redirects back with a one-time authorization code.
  4. The SPA exchanges the code plus the original verifier for tokens. PKCE proves that whoever started the login is the one finishing it, so a stolen code is useless.
  5. The SPA calls /api/cities with Authorization: Bearer <access token>.
  6. The API checks the token's signature (with Keycloak's public keys, downloaded once from /.well-known/openid-configuration), its issuer, its audience (is it meant for this API?) and its expiry, then reads the roles.
Inside a JWTThree base64url parts: header.payload.signature. The payload holds claims such as sub (user ID), iss, aud, exp and roles. It is signed, not encrypted: anyone can read it (try jwt.io with a test token), but nobody can change it without breaking the signature. Never put secrets in it.
Other flows you will meetClient credentials (machine to machine, no user): partners calling the partner API, phase 5. The MCP server uses OAuth for remote clients (phase 5–6).
Watch outAccess tokens are short-lived (minutes). Refresh happens through the OIDC library. Tokens in localStorage can be stolen by any cross-site scripting bug, so prefer memory or session storage, or a BFF (decision 10). Always validate aud, or a token issued for another app would be accepted. Never accept unsigned tokens (alg: none).
Readoauth.net/2 (overview of flows), "OAuth 2.0 for Browser-Based Apps" (IETF), the Microsoft docs on JWT bearer authentication in ASP.NET Core, and Keycloak's "Getting started with Docker".

Authentication vs authorization, roles and policies Task 7

Containers, images, multi-stage builds Deep diveTask 10

An image packages an app with everything it needs to run (runtime, libraries, files). A container is a running instance of an image, isolated from other processes.

Why we need it here"Works on my machine" disappears: the image that passed tests in CI is exactly what runs on test and in production. Kubernetes only runs containers.
How it worksA Dockerfile is a recipe of layers. Each instruction adds a cached layer, so put rarely-changing steps (restore packages) before often-changing ones (copy source) to keep rebuilds fast. A multi-stage build uses a big SDK image to compile, then copies only the published output into a small runtime image (task 10). The final image holds no compiler, no source, no test code: smaller, faster to pull, and less to attack.
In this projectImages: agency-api (BackOffice host), agency-migrator, agency-web (nginx + built SPA), and later one per host. .NET images listen on port 8080 by default and include a non-root app user. docker compose runs the whole system locally with one command. The .NET SDK can also build images without a Dockerfile (dotnet publish /t:PublishContainer), but write the Dockerfile once so you understand it.
Watch outAdd a .dockerignore (bin/, obj/, node_modules/, .git), or the build context becomes huge and may leak files. Never bake secrets into an image: anyone who can pull it can read them. Containers are disposable, so never write important files to the container's disk.

Container registry and image tags Task 12

A registry stores images (GHCR, ACR). A tag names a version of an image.

In this projectCI pushes ghcr.io/<org>/agency-api:<git-sha>. The commit SHA makes every tag unique and traceable to the exact code. Helm deploys that SHA. Avoid deploying :latest: you cannot tell what is running, and rollbacks become guesswork.

Kubernetes core objects: Pod, Deployment, Service Deep diveTask 11

Kubernetes runs containers across machines and keeps reality equal to what you declared: "I want 2 copies of agency-api version X, reachable at this name".

Declarative modelYou do not run commands like "start a container". You submit YAML describing the desired state. Controllers in the cluster constantly compare desired with actual state and fix the difference: a crashed container is restarted, a lost node's pods are recreated elsewhere.
ObjectWhat it isIn this project
PodThe smallest unit: one (or a few tightly coupled) containers with a shared IP. Disposable and replaceable at any time.One API container per pod.
DeploymentKeeps N identical pods running (through a ReplicaSet) and replaces them gradually on a new version.api (2 replicas), web (2 replicas).
ServiceA stable internal name and IP that load-balances to the pods matching a label selector. Pods come and go, but the Service stays.api → pods labelled app=api, port 80 → 8080.
Ingress / GatewayHTTP(S) routing from outside the cluster to Services, by host name and path. Needs a controller installed./api → api Service, / → web Service, TLS.
ConfigMap / SecretConfiguration given to pods as environment variables or files. Secrets are for sensitive values.Auth settings, config.json for the SPA / connection string.
Job / CronJobPods that run to completion, once or on a schedule.Migrator Job per release. Nightly checks later.
NamespaceA named partition of a cluster: names, permissions and quotas per environment.agency-local, agency-test, later agency-prod.
Watch outPods are cattle, not pets: no state on local disk, any pod can die at any time. That is why ASP.NET Core Data Protection keys must be shared (Redis, phase 3) once you rely on cookies, and why concurrency must be safe in the database. kubectl describe pod and kubectl logs are your first debugging tools. The Events at the bottom of describe usually explain the problem (image pull failure, failing probe, out of memory).
Readkubernetes.io/docs/tutorials ("Learn Kubernetes Basics"), then the Concepts pages for each object.

Liveness, readiness and startup probes Task 11

Kubernetes calls your health endpoints to decide whether to restart a pod (liveness) and whether to send it traffic (readiness).

In this projectLiveness → /health/live (no dependencies). Readiness → /health/ready (includes PostgreSQL). If the database blips, pods become not ready (no traffic) but are not restarted. If liveness checked the database, a database outage would make Kubernetes restart every pod in a loop, which makes the outage worse. A startup probe gives slow starts time before liveness kicks in.

Resource requests and limits Task 11

Requests are what the scheduler reserves for a pod. Limits are the maximum it may use.

In this projectStart modest (for example API: request 100m CPU / 256Mi memory, memory limit 512Mi) and adjust from real metrics. A pod above its memory limit is killed (OOMKilled in describe). .NET reads the container's memory limit and sizes its garbage collector accordingly. Without requests, the scheduler packs pods blindly.

Helm: charts and values Deep diveTask 11

A package manager and template engine for Kubernetes YAML. A chart is a folder of templates. Values files fill them in per environment.

WhyLocal, test and production need the same objects with different host names, replica counts, image tags and secret names. Copying YAML three times drifts. With Helm: one chart, one values file per environment.
# templates/api-deployment.yaml (excerpt)
spec:
  replicas: {{ .Values.api.replicas }}
  template:
    spec:
      containers:
        - name: api
          image: "{{ .Values.image.registry }}/agency-api:{{ .Values.image.tag }}"
          envFrom:
            - secretRef: { name: {{ .Values.database.secretName }} }
          readinessProbe: { httpGet: { path: /health/ready, port: 8080 } }
          livenessProbe:  { httpGet: { path: /health/live,  port: 8080 } }

# values-test.yaml
api: { replicas: 2 }
image: { registry: ghcr.io/your-org, tag: "set-by-ci" }
database: { secretName: agency-db }
Commandshelm template renders locally (read the output!). helm upgrade --install installs or upgrades a release. helm history and helm rollback undo a bad release. Hooks (pre-install, pre-upgrade) run Jobs such as the migrator before the new version rolls out.
Watch outTemplate whitespace and indentation errors are common. Run helm lint and helm template in CI. Hook ordering versus Secrets: see the gotcha in task 11.

Ingress, Gateway API, cert-manager and TLS Tasks 11, 12

Ingress (and its successor, the Gateway API) routes outside HTTP traffic to Services. cert-manager obtains and renews TLS certificates automatically (for example from Let's Encrypt).

In this projectOne host name per front end, /api routed to the API (same origin, no CORS). A ClusterIssuer for Let's Encrypt. Certificates renew without anyone remembering. See the ingress-nginx retirement box in C2 before choosing a controller.

Rolling updates and rollbacks Task 12

A Deployment replaces old pods with new ones gradually, sending traffic only to pods that are ready, so there is no downtime.

In this projectThis only works if readiness probes are honest, and if old and new versions can run side by side for a moment against the same database schema ("expand → contract" migrations, E3). Undo with helm rollback, or by redeploying the previous SHA.

kind: Kubernetes in Docker Task 11

A full Kubernetes cluster running as Docker containers on your laptop. Free, disposable, and identical in API to a cloud cluster.

In this projectLearn and debug the Helm chart locally before paying for cloud. Images built locally must be loaded into kind (kind load docker-image). To reach an Ingress on kind, the cluster config maps ports 80/443 to your machine (extraPortMappings). kind delete cluster and start again whenever you are lost: that is the point.

CI/CD with GitHub Actions Deep diveTasks 2, 12

Continuous integration: every push is built and tested automatically. Continuous delivery/deployment: every merge to the main branch produces images and deploys them to the test environment.

How GitHub Actions worksA workflow (.github/workflows/*.yml) is triggered by events (pull_request, push). It contains jobs that run on fresh runners (virtual machines), and each job is a list of steps: shell commands, or reusable actions (actions/checkout). Jobs run in parallel unless one needs another.
In this projectci.yml on every PR: backend build + tests (including Testcontainers), front-end type check + lint + tests + build, OpenAPI client drift check, Helm lint. cd.yml on merge to main: build and push images tagged with the SHA, run helm upgrade --install against agency-test. Branch protection makes the CI check mandatory before merging.
Watch out
  • Give the workflow's GITHUB_TOKEN only the permissions it needs (permissions: block, for example packages: write for GHCR).
  • Prefer OIDC federation to the cloud over storing long-lived cloud credentials as secrets.
  • Pin third-party actions to a version (ideally a commit SHA). An action is code that runs with your secrets.
  • Cache NuGet and pnpm stores to keep runs fast.
  • Keep production deployment behind a manual approval (GitHub "environments") when you get there.
Readdocs.github.com/actions ("Understanding GitHub Actions", "Security hardening for GitHub Actions").

Managed PostgreSQL and Redis Task 12

The cloud provider runs the database server: patching, backups, point-in-time recovery, failover. You get a connection string.

In this projectADR 0004: billing data must not be lost, so production PostgreSQL is managed, outside the cluster. For local and kind, a PostgreSQL container is fine because the data is disposable. Before go-live, test a restore: a backup you have never restored is a hope, not a backup. Require TLS on the connection and allow only the cluster's network.

E7. Git and pull requests

Branches, commits, pull requests Task 0

Every change is made on a short-lived branch, reviewed as a pull request and merged into main, which must always be deployable.

HabitsSmall commits that each build. Messages in the imperative that say why ("Add unique index on city name to prevent duplicates under concurrency"). Stage with git add -p so you read every hunk. Squash-merge PRs for a clean history. Delete merged branches. Rebase your branch on main if it falls behind (git pull --rebase origin main).
Reviewing your own PRRead the diff on GitHub as if a stranger wrote it. Check it against the definition of done (B4). With AI-written code, ask: does it follow CLAUDE.md? Did it add a dependency? Did it invent an API that does not exist? Is every new branch of logic tested?
